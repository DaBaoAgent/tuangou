# 团购项目审计（2026-11-10）

审计范围：`scripts/publish/`、`scripts/auto-edit/`、`素材库/`、`runtime/publish/`、账号近 30 天数据。
结论分三类：**能不能出单**、**能不能自己跑下去**、**今天已经改了什么**。

## 一句话结论

链路本身是通的（54 条自动发布、0 次重复发布），但此前**没有一条视频挂过团购商品**，文案却在反复说「戳链接」——观众点不到任何东西，所以有播放也出不了单；同时**未剪素材已经为 0**，现有 75 条成片按每天 5–8 条只能再撑 10–14 天，之后整条管线会自然停摆。

## 二、出单链路：断在哪

### P0-1 从未挂载团购商品（今天已修）

证据：
- 内容管理页关键词计数：`商品标签` 0、`已挂载` 0、`购物车` 0、`带货` 0。
- `publish_one.js` 全流程只有「位置门店」，从来没有进过「团购商品」选择器。
- 文案模板大量出现「现在戳链接」「赶紧戳链接」，但页面上没有可点的商品。

影响：成交无法直接归因到视频，用户要多一跳（点门店 → 找团购）。**2026-11-10 22:45 更正：这不是「零出单」的原因。**手机端「数据中心 → 交易分析」显示，只挂门店的一周里仍成交 28 单 / ¥326.87、核销 17 单、佣金 ¥3.09（成交全部落在近 7 日窗口 11/3–11/9 内；因近 7 日与近 30 日数字相同，只能确定更早没有成交，不能确定具体哪天）。此前「商品标签计数为 0 所以没出单」是被网页口径误导——创作者中心没有团购分类，电商口径自然为 0。挂商品的真实收益是少一跳 + 归因清晰，不是从 0 到 1。

修复：`publish_one.js#setProduct()` + `product_pick.js`，发布时优先挂商品，挂不上才退回门店（详见 README「发布流程」）。实跑校准（2026-11-10 21:46）：入口是标签行「位置」→ 下拉「团购」→「请选择团购商品」；点选后还要在抽屉里填推广标题、选「仅推荐同品牌商品」、点「添加」才算挂上，否则遮罩会挡住自主声明。`publish_one.js --dry-run` 全流程通过：袁记云饺商品 ￥9.9、佣金 3%，AI 声明与「不同时发布」预检正常；新增 `product_attach.test.js`（3 项）复现该层级。

### P0-1b 锚点该挂团购商品还是只挂门店（2026-11-10 调研）

发布页的「位置」是同一个锚点位的类型选择（下拉：位置 / 团购 / 购物车 / …），团购和普通位置二选一，不能同时挂。挂上团购商品后锚点自带门店（商品卡显示「等 N 店通用」），位置不会丢；只挂位置则用户要先落到 POI 落地页、再找团购、再下单，多一跳。

证据：① 2024-07-22 抖音改版把 POI 页改成「打卡 / 附近吃喝玩乐内容」，商品货架被拿掉，纯 POI 的成交能力被主动削弱；② 2022H1 短视频挂团购链接已占抖音本地生活 GTV 近 70%；③ 晚点 LatePost 数据，搜索带来的下单率约为刷视频直接下单的 10 倍，2025 年 11 月搜索下单 GMV 占比超 50%；④ CBNData 2025 年约 80% 用户主动搜优惠、贡献约 55% 交易额；⑤ 本账号 54 条只挂门店的作品，内容管理「商品标签 / 已挂载 / 购物车 / 带货」计数全为 0；手机端显示只挂门店一周仍成交 28 单，说明门店路径能成交但要绕路，且成交不会归到视频上。

结论：**默认挂团购商品，门店只做兜底和曝光**（挂不上商品、投本地推、养 POI 质量分时才用门店）。配套整改：推广标题从品牌名改成 `promoTitle()` 派生的「商品名+规格」（≤10 字，如 `【专属特惠】熟食·冬菇马蹄云饺2选1` → `冬菇马蹄云饺2选1`），以贴合 2025–2026 锚点新规「锚点标题贴近商品、商品需在画面中出现」。来源见 `scripts/publish/README.md`「为什么优先挂团购商品而不是只挂门店」。

### P0-2 前 2 秒留不住人

近 30 天 62 条作品：**2s 跳出率 62.4%，完播率 4.5%，5s 完播 11.7%**。
这意味着六成以上的人在第 2 秒就划走。当前文案开头是「鸡柳薯条年糕三合一，看饿了没？」这类铺垫，第一帧没有价格、份量或成品特写。

建议（需要人工改剪辑结构，不是文案能修的）：开头 1.5 秒直接给「成品特写 + 价格 + 份量」，把 CTA 放到最后 3 秒；总时长压到 15 秒内。

### P0-3 播放量处于低位，且无法区分「限流」还是「冷启动」

- 近 30 天 62 条：播放合计 9,638，单条均播 **155**；最好一条 1,105。
- 「数据中心」仪表盘：账号 7 日总播放 8,089，较前 7 日 **-5.32 万**；净增粉丝 -133（吸粉 5、脱粉 138）。这两项来自仪表盘，不能从 `works.json` 导出表复算——仪表盘按日历窗口统计全部作品播放，导出表是每条作品的累计播放。
- 132 条作品里，2025–2026 年的老作品播放量导出为 0、点赞却上万（西瓜迁移内容），说明这个号是靠老内容带量的账号，新垂直内容进入了冷启动。

两种可能：账号被判定低质/搬运，或只是新内容没有初始推荐。**需要一次受控实验来区分**：连续 3 天、每天 3 条、不同品牌、全部挂商品、开头改成价格/成品特写，观察 24 小时播放能否稳定突破 500。如果仍然只有几十，就按限流处理（降频、提高原创度、加真人出镜）。

## 三、自主运行：哪里会停

### P0 源素材为 0（唯一硬停点）

- `素材库/未剪素材` 顶层文件数 **0**，只有 `已剪/` 里的 83 条历史源素材。
- `素材库/已剪成片` 现有 75 条，发布队列可用 74 条。
- 当前节奏 5–8 条/天 → **约 10–14 天后无片可发**；`prepare.js` 会每小时尝试补货，但没有源素材，只能反复通知「库存为空」。

需要宝哥决定的供给方式（任选）：继续手动丢素材到 `素材库/未剪素材`；或接百度同步盘新批次；或扩大素材采集渠道。

### P1 发布核实拿不到作品 ID

54 条已发布记录里 `work_id` **全部为 null**。核实步骤依赖内容管理页里的 `work-detail/<id>` 链接，实际 DOM 里没有（日志全部 `id=none`）。
后果：作品数据只能靠「标题前缀」回连计划，标题被平台改写或重复时会对不上。这不是发布失败，但会削弱数据闭环。下一步：从内容管理卡片的「编辑作品」链接或接口响应里抓真实 ID。

### P2 品牌待确认依赖人工回填

品牌闸门是硬闸门（无品牌/待复核/置信度<0.9 一律不进队列），设计上正确；但被拦下的成片需要人工改 `meta.json` 才能回队。当前没有「待确认清单自动汇总成一条消息」的机制，只有移动时的 Toast。

### P2 浏览器档案是单点

发布、数据采集、扫码登录共用 `runtime/browser-profile`。已用 `run.lock` 让数据采集在发布时让路，但两个任务若同时启动仍可能争抢档案（Playwright 会直接启动失败）。目前靠时间错开（采集 09:20 / 21:20）规避。

### P2 桌面通知是唯一告警通道

微信推送已于 2026-11-08 停用。现在失败/暂停只弹 Windows Toast；人不在电脑前就看不到。审计不擅自改回，但如果希望「无人值守也收得到告警」，需要重新选一个通道。
