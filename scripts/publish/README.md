# 自动发布模块

无人值守把 `素材库/已剪成片` 的成片发布到抖音创作者中心，发布后归档到 `已剪成片/已发`。图文模块已暂停，本目录只服务视频。

## 文件

| 文件 | 作用 |
|---|---|
| `config.json` | 路径、排期窗口、文案上限、发布开关 |
| `lib.js` | 排期生成、库存索引、品牌/商品词识别、文案生成 |
| `publish_one.js` | 单条发布全流程（Playwright 无头 Chromium） |
| `run_due.js` | 定时入口，每 5 分钟发布最多 1 条到期作品 |
| `subtitle_gate.js` | 发布前字幕闸门：按成片来源做 OCR 复核，失败移入 `字幕待修复`，新片未复核不进队列 |
| `prepare.js` | 库存不足时 `--all` 补货；空闲时窗口外 `--all` 清完、窗口内一次剪一条；已有 auto_edit 进程时跳过 |
| `product_pick.js` | 团购商品挑选规则：**先按视频文案里的商品名硬匹配，命中者优先；一条都不命中就不挂商品**；品牌匹配、排除非餐饮、偏好爆款/强促销/低门槛价格带（2026-11-10 起不按佣金率排序）；`promoTitle()` 从商品名派生 ≤10 字推广标题 |
| `product_attach.test.js` | 团购商品挂载回归（本地 HTML + Chromium）：标签行「位置」入口、品牌过滤、抽屉填「商品名+规格」推广标题并添加 |
| `queue_score.js` | 发布队列打分与时段加权（品牌历史播放、出单、品类质量、库存新鲜度） |
| `analytics.js` | 作品数据解析与聚合：xlsx → 按品牌/品类/时段画像，写入 `runtime/publish/stats/works.json` |
| `xlsx.js` | 零依赖 xlsx 读取（ZIP + sharedStrings + sheet1） |
| `stats_fetch.js` | 数据采集：用已登录档案打开内容管理 → 导出数据 → 解析 → 生成周报，顺带采集收入 |
| `stats_report.js` | 周报文字与建议生成（`runtime/publish/stats/report.md`） |
| `revenue.js` | 收入采集：点开「收入变现」的金额遮挡开关，读总览 KPI 与「选品带货/内容付费」等分类，写入 `runtime/publish/stats/revenue.json` |
| `revenue.test.js` | 收入解析回归：遮挡态返回 null、分类四口径、千分位 |
| `login.js` | 首次/失效后扫码登录，持久化 profile |
| `publish.test.js` | `node --test` 回归测试：排期、文案过滤、乱码黑名单、长度与话题 |
| `publish_settings.test.js` | 发布设置回归（本地 HTML + Chromium）：必须选中「不同时发布」，取消并复核今日头条/红果短剧同步项 |
| `run_due.test.js` | 沙箱端到端测试：dry-run 无副作用、点击发布后遇验证码不重发、排除表生效 |
| `subtitle_gate.test.js` | 字幕闸门回归：存量放行、新片复核、失败移入待修复、缺校对稿暂缓、缓存复用 |
| `analytics.test.js` / `queue_score.test.js` / `product_pick.test.js` | 数据解析、队列打分、商品挑选的纯函数回归 |
| `notify.ps1` | Windows Toast 通知 |

## 运行状态

- 计划任务：`TuangouPublish`（每 5 分钟）、`TuangouPrepare`（每 30 分钟检查，全天运行）、`TuangouStats`（每天 09:20 / 21:20 采集账号数据，发布进行中自动让路）
- **后台独立运行**：两个计划任务直接调用 `node.exe`，不依赖 Claude Code 会话，关掉 Claude Code 窗口后继续剪辑和发布
- **电池策略**：已关闭「使用电池时禁止启动」和「切换到电池时停止」，笔记本拔电后计划任务照常运行
- 剪辑空闲判定：发布窗口外一次清完未剪素材；窗口内距下一个待发作品 60 分钟以上且没有发布进行中，每次剪一条；刚复制进来的素材要等 2 分钟稳定后再剪
- 运行时数据：`runtime/publish/state.json`、`runtime/publish/plans/YYYY-MM-DD.json`、`runtime/publish/logs/YYYY-MM-DD.log`
- 浏览器 profile：`runtime/browser-profile`；Chromium 路径（A4）：环境变量 `TUANGOU_CHROMIUM` → `config.publish.chromium_path` → 扫 `ms-playwright/chromium-*` 取最高版本 → playwright 自带

## 排期规则

- 第 1 天 2 条、第 2 天 3 条、第 3 天 4 条，之后固定每天 8 条（`schedule.ramp` / `steady_min`=`steady_max`=8；2026-11-14 宝哥从 3–5 条上调，原 2026-11-11 的降量设定作废）
- 时间窗 06:00–19:00，相邻作品最小间隔 80 分钟（`schedule.min_gap_minutes`，2026-11-14 由 90 下调，给 8 条留出排布空间）；同一天可复现（seeded random）
- **同品牌冷却 + 每日上限（2026-11-11 宝哥拍板）**：同一品牌发过之后 `schedule.brand_cooldown_minutes`（默认 240 分钟）内不再发；同一品牌每天最多 `schedule.brand_daily_cap`（默认 2 条）。数据源是最近两天的计划里 `status=published` 的条目（`lib.js#brandUsage()`），跨午夜照样算冷却。被挡住的成片留在队列里，换下一个品牌；全部品牌都在冷却时本轮跳过并每小时最多通知一次，绝不为填坑连发同品牌
- 当天首次建计划时若随机时间已过，剩余时间压缩到「现在 +5 分钟 ~ 19:00」
- **时段加权（2026-11-10）**：`publish.use_hour_profile` 打开且账号画像样本 ≥30 条时，按各时段历史单条均播加权投放到更好的时段；样本不足或没有画像时退回上面的均匀随机。实测 2026-11-10：09–12 点均播 221，06–09 点只有 54，权重自动把排期往上午倾斜

## 发布流程

上传 → 标题/简介/话题 → 封面（竖 3:4，横封面由抖音自动生成）→ **团购商品（优先）→ 门店（兜底）** → 自主声明「内容由AI生成」→ 预检 → 发布 → 内容管理按标题核实 → 移入 `已发`。

团购商品挂载（2026-11-10，`publish.attach_product`）：**标签行里的「位置」**（不是「输入地理位置」，后者只开 POI 搜索、没有团购入口）→ 下拉「团购」→「请选择团购商品」→ 输入品牌过滤 → 按 `product_pick.js` 规则选一条（**商品名必须先对得上文案，见下条硬规则**；品牌必须对得上、排除影院/足浴等非餐饮、偏好爆款/强促销/低门槛价格带、避开次卡储值；2026-11-10 起不再按佣金率排序）→ 抽屉里填「推广标题」（`product_pick.js#promoTitle()` 从商品名派生的「商品名+规格」，≤10 字；2026-11-10 起不再只写品牌名）→ 选「仅推荐同品牌商品」→ 点「添加」。只有点完「添加」商品才真正挂上，抽屉遮罩消失，才能继续做自主声明和预检。挂上商品后定位跟商品走，不再单独挂门店；挂不上就退回只挂门店，并在发布成功通知里写明「未挂团购商品」。挂商品的价值是少一跳、成交直接归因到视频；**它不是从 0 到 1**——只挂门店一周也成交了 28 单（见「账号数据」）。2026-11-10 21:46 已用 `publish_one.js --dry-run` 实跑验证：袁记云饺商品 ￥9.9、佣金 3%，后续 AI 声明与「不同时发布」均正常。

**选品硬规则（宝哥 2026-11-11 固化）：选品以视频文案里的商品名为准，商品名对不上就不挂商品。** `decideProduct()`（`product_pick.js`）先从 `meta.brand.product` 取商品名，缺省用文案里识别出的商品词（`buildCopy()` 的 `copy.product`，`run_due.js` 已写进计划）；`productTerms()` 把商品名归一化成匹配词——去掉营销括号、价格、标点、空格，剥掉品牌前缀和「2选1 / 大杯 / 套餐」这类规格后缀。列表里的商品卡按同样的规则归一化后做包含匹配：**命中者优先，命中词越长分越高**（「莓果酸奶饮」>「莓果」），同品牌的其他爆款/低价商品不会因为分高被选中。如果文案商品在列表里一条都匹配不到，返回 `product-mismatch`，**退回只挂门店并在日志/通知里写明原因，不允许改挂同品牌的其他商品**。商品名缺省、或商品名本身就是品牌名/「套餐」「代金券」这类泛词时，视为文案没指定商品，才对整个品牌级列表按爆款/价格带挑（兼容老行为）。回归用例见 `product_pick.test.js` 的「硬性规则」四条。

预检要求「同时发布」设为「不同时发布」：必须读到明确选中状态，且「同步到今日头条」「同步到红果短剧」均未被勾选，才放行；脚本会先主动取消这些同步项再复核，读不到状态或有同步项残留时会再确认一次，仍不满足就不发布。品牌已确认时「团购商品」或「门店标签」至少要挂上一个，都挂不上就不发布，成片留队重试/通知，绝不裸发。点击「发布」之后，无论随后遇到验证码、登录失效还是页面未确认，一律按「结果待核实」处理：成片加 `_unverified_` 前缀移出自动队列、计划标 `pending_verify`、通知人工核实，绝不自动重试；改名失败时把成片写进 `state.excluded_videos`，同样不会再被选中。审核不通过同理移出队列。

文案质量闸门：片尾口播（点赞/订阅/打赏/栏目/感谢观看等）、纯英文行、口吃重复、从半句开始的碎片会被过滤；常见 ASR 同音错字（豚→囤、买一送衣→买一送一、粉紫便便→粉紫渐变等）自动纠正；标题至少包含一个卖点词，否则用 meta 里的商品名兜底。标题或描述命中乱码/低俗词（如「特大粪」「赤道称」「我操」「尼玛」「拉屎」等）、控制字符或换行，标题含非白名单字符或纯标点时，整条成片不自动发，换下一条，并每小时最多通知一次。

品牌闸门：无品牌、`needs_review=true`、或置信度低于 `publish.brand_min_confidence`（默认 0.9）的成片一律不放行；跳过后继续发下一条品牌能确定的，发布成功通知里会列出跳过的成片名。品牌不能确认的成片会被自动移入 `品牌待确认`（见下节），不留在自动发布队列。品牌确认后不论 `verified` 是否 true 都挂位置门店，未认证品牌只是不挂品牌话题。OCR 对仿品牌字不可靠（`11月1日_00791652.mp4` 被读成 McS/McSa，宝哥确认为肯德基），人工核验要联网多搜索到能确定为止，仍不能确定就放弃该条，绝不猜着发。

品牌核实规则（宝哥 2026-11-10 固化）：**新品牌能联网查证的自己查，不要问宝哥**。用 WebSearch 至少两路证据（官网 / 百度百科 / 大众点评门店 / 行业媒体报道任取其二），能对上就把 `scripts/auto-edit/brands.json` 的 `verified` 置 `true`，在 `note` 写清核实依据和日期；查不到就保持 `verified: false` 并在 note 写「联网未查到」，按未认证品牌继续走（挂门店、不挂品牌话题），不要停机等确认。

联名款商户认定（2026-11-10）：品牌识别可能把联名方之一当成 brand，但团购要挂的商户是**开店的那一方**。例如「袁记云饺×三养火鸡辣酱」，商户是袁记云饺，三养是预包装食品品牌、没有本地生活门店。认定结果要**固化**到 `runtime/auto-edit/brand_overrides/<素材文件名>.json`（写 `brand` / `product` / `note`，优先级最高，重剪重跑都不会退回 needs_review），并把 `runtime/auto-edit/work/<dir>/meta.json` 的 `brand` 与 `runtime/auto-edit/brand_index.json` 对齐；只改 meta 会被下一次重渲覆盖。

位置是硬闸门（2026-11-10 澄清）：`publish_one.js` 在品牌已确认但「团购商品 + 门店」都没挂上时直接返回 `location-missing`，留队重试。`config.publish.location_fallback` 是历史遗留的死配置，代码从未读取，已删除；不要再以为它能让无门店品牌放行。

品牌待确认归档（宝哥 2026-11-04 固化，自动执行）：`lib.js#quarantineUnconfirmed()` 在每轮 `run_due.js` 开始时扫描 `已剪成片` 顶层，凡品牌闸门不通过的成片自动移入 `素材库/已剪成片/品牌待确认/`（子目录不被 `listVideos` 扫描，等于移出自动队列），同步更新该条 `meta.json#output` 与 `brand_index.json`，并桌面通知移入清单；`--dry-run` 只报告不移动。回退备份见 `runtime/auto-edit/backup-quarantine-20261104/`。处理方式（宝哥 2026-11-11 指令：「品牌待确认的以后不用问我，自己联网查证后解决」）：**不再等宝哥确认**，按上条核实规则自己联网查；查实的写成 `brand_overrides` 并按新品牌重渲（或改 `meta.json` 的 `brand`、`source: manual`、`confidence: 1`、`needs_review: false`），再重算 `brand_index.json`，把成片按原文件名移回 `已剪成片` 即可重新入队。`待确认清单.md` 逐条记录画面商品、疑似品牌和不能确认的原因。2026-11-11 实测：`品牌待确认` 已清空（8 条按核实结果重渲入队），`quarantineUnconfirmed({dryRun:true})` 返回 0。

字幕闸门（宝哥 2026-11-04 固化，自动执行）：`subtitle_gate.js#auditInventory()` 在每轮 `run_due.js` 里、发布前扫描 `已剪成片` 顶层，按成片来源选择复核依据——自动剪辑成片按 `meta.lines`（即烧录字幕的来源）逐行 OCR；修字成片按 `subtitle_repair.corrections` 复核；`subtitle_skipped` 的成片直接放行。复核由 `scripts/auto-edit/audit_clip.py` 调用 Dabao-OCR 常驻服务完成：每条字幕取中点裁字幕带识别，失败再裁紧带高清重查，期望行与识别文本相同或相似度 ≥ 0.75 才算通过。

处理规则：复核对不上的整条移入 `素材库/已剪成片/字幕待修复/`，同步更新 `meta.output` 与 `brand_index.json`，并发通知，绝不自动发；没有校对依据的手工新片（`external`）和无声明的成片标记 `manual`，只暂缓发布、不移动，等人确认；OCR 服务不可用时同样暂缓。`confirmed()` 只放行缓存中 `ok / skipped / legacy_ok` 的成片，`run_due.js` 会跳过未确认的成片继续发其他可发片，全部被封时计划保持 `pending` 并每小时提醒一次。

`publish.subtitle_enforce_since`（默认 `2026-11-04T19:00:00+08:00`）之前的存量成片按 mtime 直接标记 `legacy_ok`，不跑 OCR；结果按文件 `mtime + size` 缓存在 `runtime/publish/subtitle_audit.json`，同一文件未变更不重复识别。修复字幕时必须按原字幕带 cover 遮盖后重打正确文本，改稿后重新渲染并替换成片，不能只改 `meta.lines`；备份和修复后成片要逐行 OCR 加全片扫描复核。`--dry-run` 只审计和报告，不移动、不写缓存。闸门校验的是「成片烧录字幕与校对稿/ASR 行是否一致」，能拦住渲染遗漏、错字残留和字幕带重影，但不能判断 ASR 初稿本身写错——没有人工校对稿的自动剪辑片仍需人工过一遍文稿，改稿后重渲。

## 为什么优先挂团购商品而不是只挂门店（2026-11-10 调研结论）

发布页的「位置」是一个锚点位的类型选择，下拉里是「位置 / 团购 / 购物车 / …」——团购和普通位置天生二选一，不存在两个都挂。挂上团购商品后锚点自带门店（商品卡显示「等 N 店通用」），位置信息不会丢。问题不是要不要位置，而是这个锚点承载哪一种。

- **要出单，选团购商品。** 商品锚点一次点击直达商品卡，是完整的成交通路；只挂位置，用户要先落到 POI 落地页、再找团购、再下单，多一跳。2024-07-22 改版后 POI 页被改造成「打卡 / 附近吃喝玩乐内容」，商品货架被拿掉，纯 POI 的成交能力是被平台主动削弱的。
- **行业数据同向。** 2022H1 短视频挂团购链接已占抖音本地生活 GTV 近 70%；晚点 LatePost 数据，搜索带来的下单率约为刷短视频直接下单的 10 倍，2025 年 11 月搜索下单 GMV 占比已超 50%；CBNData 2025 年约 80% 用户主动搜优惠、贡献约 55% 交易额。这些都要靠一个结构化商品来承接。
- **本账号实证（2026-11-10 22:45 更正）。** 54 条已发布作品全部只挂门店，内容管理里「商品标签 / 已挂载 / 购物车 / 带货」计数均为 0——但手机端数据显示，只挂门店一周也成交了 28 单（见下节），所以「没挂商品 = 零出单」并不成立。挂团购商品仍然是默认做法，理由是它在同一个锚点位里少一跳、成交直接归因到视频，而不是因为门店不出单。
- **门店仍然要用的场景**：挂不上品牌匹配商品时的兜底；要投巨量本地推（只有挂了 POI 团购锚点的视频才能投，默认只投门店 6 公里）；纯同城种草、养 POI 质量分。这些服务的是曝光目标，不是出单目标。

推广标题随之整改（2026-11-10）：平台限 10 字，新规要求锚点标题尽量是「商品名称+规格」。`promoTitle()` 会去掉 `【专属特惠】` 这类营销括号、价格和「熟食 / 生鲜」泛品类前缀，例如 `【专属特惠】熟食·冬菇马蹄云饺2选1` → `冬菇马蹄云饺2选1`；取不到有效内容才退回品牌名。只写品牌名（如「袁记云饺」）在新规下更容易被判「标题与商品不相关」。另外新规要求锚点商品在画面中实际出现，剪辑侧要保证所选商品的实物有镜头。

参考：[抖音打卡锚点与 POI 的区别](https://www.sohu.com/a/800579492_121858230)、[抖音本地生活核销率与搜索转化](https://www.huxiu.com/article/4848712.html)、[抖省省与 80% 搜索用户](https://www.cbndata.com/information/295223)、[短视频挂团购链接占 GTV 近 70%](https://pdf.dfcfw.com/pdf/H3_AP202310121601260883_1.pdf)。

## 账号数据与智能队列（2026-11-10）

数据来源：`stats_fetch.js` 用同一个已登录浏览器档案打开创作者中心「内容管理」，点「导出数据」，把下载到的 `作品列表导出.xlsx` 解析成 `runtime/publish/stats/works.json`，同时生成 `runtime/publish/stats/report.md` 并弹通知。计划任务 `TuangouStats` 每天 09:20 / 21:20 各跑一次；`run.lock` 存在时自动让路，不抢同一个浏览器档案。

导出表的三个坑，代码里已经处理：
1. **没有作品 ID**：只能靠「作品名称」join 计划里的 `copy.title`；导出表的名称是「标题+描述+话题」整段，所以用最长前缀匹配（`analytics.js#matchPlan`）。
2. **播放量只反映近期窗口**：账号里 2025–2026 年的老作品播放量是 0、点赞却上万（西瓜迁移内容），直接算均值会把数据拖死；统计默认只看最近 30 天（`publish.analytics_window_days`）。
3. **封面点击率常为 `-`**：解析成 `null`，不参与均值。

收入数据（`revenue.js`）：创作者中心「收入变现」的金额默认被遮挡——渲染成 data-URI 图片，OCR 只能读到 `******`；页面上有一个 `eye_closed` 图标，点开后才变成真实数字。`revenue.js` 先点开再解析，`stats_fetch.js` 每次采完作品数据顺带跑一遍，写入 `runtime/publish/stats/revenue.json`。

### 当前优化目标（2026-11-10 宝哥定）

先把号做起来：**播放量 > 团购等级 > 出单量**，暂不看佣金和利润。落到代码上：

- `queue_score.js` 仍按品牌历史播放（35）+ 订单（45）+ 品类质量/新鲜度加权，佣金率不参与；`orders.json` 有数据后订单权重立即生效。
- `product_pick.js` 自 2026-11-10 起不再按佣金率排序，只按品牌匹配、爆款/促销词、价格带、是否次卡来选；0 佣金但好卖的爆款也会被选中。
- 团购等级是「达人带货力等级」：Lv0–Lv8，自然月统计，每月 6 日按上一自然月评级并展示到次月 5 日；视频侧看交易额/核销数、播放量前 10 的视频播放、稿均播放与交易额、本地商户探店量与核销数。虚假交易/搬运/作弊数据会被剔除；严重违规或信用分 <60 记 Lv0。只在手机端「我 → 团购带货 → 团购达人中心」可见，web 没有该页。参考：[抖音生活服务达人带货力新等级体系上线](http://ex.chinadaily.com.cn/exchange/partners/82/rss/channel/cn/columns/sz8srm/stories/WS66b1e650a310054d254ebb3e.html)。
- 由此推出一条硬约束：**堆量发低播放视频会拉低稿均，反而拖等级**。同品牌同日连发（11-10 一天 7 条鸡柳大人）和每天 5–8 条的低质成片要收敛；「2 秒跳出 62%」的开头结构比发片数量更值得改。
- 2026-11-11 已落地三项配套：① 排期降到每天随机 3–5 条、最小间隔 90 分钟；② 同品牌冷却 240 分钟 + 每日上限 2 条（`run_due.js` 在打分排序之后、选片之前过滤）；③ 剪辑侧开头 1.5 秒结构（推近运镜 + 钩子卡，见 `scripts/auto-edit/README.md`）。

出单数据：`buyin.jinritemai.com` 在当前档案下未登录，团购订单 web 也拿不到。现在用手机端作品列表截图折算成 `runtime/publish/stats/orders.json`（2026-11-10 首份：CoCo都可 ~10 单、临榆 ~5、沪上阿姨 ~4、茶百道 1、瑞幸 1；订单数为估算，gmv/佣金为实测），队列会把订单权重拉到最高。也可以从巨量百应/精选联盟（达人侧）或抖音来客（商户侧）导出后覆盖同一文件：

```json
{ "updated_at": "2026-11-10T21:00:00+08:00",
  "brands": { "袁记云饺": { "orders": 12, "gmv": 456, "commission": 13.6 } } }
```

也接受数组格式 `[{ "brand": "...", "orders": 1, "gmv": 10 }]`。

队列打分（`queue_score.js`）：`base 20 + 品牌历史播放 35 + 订单 45 + 品类质量 10 + 已认证 4 + 有商品名 3 + 优先品牌 8 + 库存新鲜度 12`，权重可用 `publish.queue_weights` 覆盖。样本 <10 条时自动退回「优先品牌 + 品牌可信度」的旧顺序，保证不会因为没数据就停发。排期时段同理（见「排期规则」）。

## 暂停与恢复

- 验证码 / 安全校验 / 登录失效：`state.json` 写入 `paused: true` 并发通知
- 恢复：重新运行 `node scripts/publish/login.js` 扫码，确认后把 `paused` 改回 `false`、`paused_reason` 置 `null`
